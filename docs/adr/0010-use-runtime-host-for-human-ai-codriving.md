# 使用独立 Runtime Host 承载人机共驾会话

## 状态

已确认，分阶段实施。

## 背景

Electron 桌面端和 MCP Runtime 目前分别构造 `SshSessionManager`。即使它们共用 SQLite，也只能共享配置和历史，不能共享 SSH Socket、PTY 当前目录、环境变量、前台进程、执行队列和待审批状态。

OrbitSSH 的产品目标已经明确为“一个执行核心、用户与 Codex 两个驾驶入口”。用户还要求关闭桌面客户端后，可以选择让 Codex 和当前会话继续运行。

## 决策

引入独立的 `OrbitSSH Runtime Host`：

- Runtime Host 唯一持有 SSH 连接、PTY、会话协调模块、审批状态和共驾事件账本；
- Electron 和 MCP 通过仅当前 Windows 用户可访问的 Named Pipe 接入；
- Electron 关闭时按用户选择释放桌面租约、等待任务结束或关闭全部能力；
- 选择 Codex 继续时，Runtime 和逻辑会话不退出；
- 高危审批只能由桌面适配器完成，MCP 不能批准自己的动作；
- 客户端重连使用逻辑会话 ID 与单调递增事件游标补回状态；
- 普通信任会话有有效期，高危操作始终需要逐项审批。

## 模块接口

桌面端和 MCP 只依赖会话协调模块的少量接口：

- 提交命令或文件动作；
- 批准或拒绝待审批动作；
- 暂停、恢复或接管 Codex；
- 设置本次会话的授权等级；
- 查询会话快照并订阅后续事件。

SSH 排队、风险评估、审批摘要、过期、来源标记和事件追加全部隐藏在该模块内部。

## 生命周期

Runtime 使用桌面、MCP、活动动作和保留会话四类租约决定是否退出。关闭界面不等于关闭 Runtime。选择“任务完成后退出”时，等待审批也属于未完成任务，但会在审批有效期结束后自动拒绝，从而避免后台永久悬挂。

## 后果

好处：

- 用户和 Codex 真正操作同一逻辑会话；
- 界面退出后 Codex 可以继续；
- 所有入口无法绕过统一授权、护栏和事件轨迹；
- UI 重开后可以恢复现场而不是新建会话。

代价：

- 需要本地 IPC 协议、单实例 Runtime、身份校验、版本握手和崩溃恢复；
- 原始交互 TTY 无法可靠预判所有用户输入，必须明确区分受保护命令模式和原始终端模式；
- 跨电脑重启保留远程交互进程需要后续 `tmux`/`screen` 适配器。

## 替代方案

继续让 Electron 与 MCP 分别持有 SSH 连接。该方案实现简单，但无法满足关闭界面后保持同一 PTY、用户接管和统一审批，因此不采用。
