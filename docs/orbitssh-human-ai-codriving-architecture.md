# OrbitSSH 人机共驾架构方案

> 状态：架构草案  
> 日期：2026-07-24  
> 适用范围：OrbitSSH Windows 桌面端、MCP Runtime 与 Codex Plugin

## 一、产品定位

OrbitSSH 不是“给 Codex 套一层 SSH”，也不只是普通终端工具，而是一个由用户和 AI 共同操作服务器的本地协作工作台。

核心目标：

- 用户可以像普通 SSH 客户端一样直接操作终端；
- Codex 可以通过 MCP 操作同一个逻辑会话；
- Codex 的命令、输出、风险和执行状态对用户完全可见；
- 用户可以审批、暂停、打断或接管 Codex；
- 所有入口执行相同的主机验证、凭据保护和历史脱敏规则。

## 二、核心架构决策

真正实现“共驾”，桌面端和 MCP 不能各自维护完全独立的 SSH 会话。

OrbitSSH 应引入独立的 `OrbitSSH Runtime Host`。Runtime Host 统一持有 SSH 连接、终端状态、执行队列和安全策略，桌面端与 MCP 作为两个适配器接入同一个执行核心。

```text
用户 ──> 桌面界面适配器 ──┐
                           ├──> OrbitSSH Runtime Host
Codex ──> MCP 适配器 ─────┘             │
                                       ├── 会话协调模块
                                       ├── 授权与风险模块
                                       ├── SSH / PTY 执行模块 ──> 远程服务器
                                       ├── 文件传输模块 ────────> 远程服务器
                                       └── 共驾事件账本 ────────> 本地 SQLite
```

如果 Electron 和 MCP 各自持有 SSH Socket，只能做到“操作记录汇总”，无法真正共享当前目录、环境变量、交互进程和终端上下文，属于表面共驾。

### 与现有方案的关系

现有《Windows 桌面应用、MCP 与 Codex Plugin 一体化设计》提出桌面端与 MCP Runtime 不跨进程共享 SSH Socket。该设计实现成本较低，但不能满足真实的人机共驾。

本方案确认实施后，应通过新的架构决策记录明确替换上述规则：

- SSH 连接由独立 Runtime Host 持有；
- Electron 窗口不是 Runtime Host；
- MCP 不直接建立 SSH 连接；
- 桌面界面关闭后，Runtime Host 可以按用户选择继续运行；
- 桌面端和 MCP 通过本地 IPC 操作同一个逻辑会话。

## 三、核心模块

| 模块 | 职责 | 对外接口 |
|---|---|---|
| Runtime Host | 统一管理进程生命周期、本地 IPC 和调用入口 | 启动、关闭、状态订阅 |
| 会话协调模块 | 管理用户和 AI 对同一会话的操作顺序 | 提交操作、取消、接管、订阅 |
| 授权与风险模块 | 判断是否允许执行以及是否需要审批 | 评估操作、签发审批、验证审批 |
| SSH / PTY 执行模块 | 持有连接、当前目录和交互终端 | 输入、执行命令、调整终端、断开 |
| 文件传输模块 | 浏览远程目录并进行有范围的上传下载 | 列目录、上传、下载、取消 |
| 共驾事件账本 | 记录操作来源、状态、结果和恢复点 | 追加事件、查询会话轨迹 |
| 配置与凭据模块 | 管理服务器配置和凭据引用 | 导入、导出、读取凭据引用 |

会话协调模块应设计为深模块：桌面端和 MCP 只依赖少量稳定接口，不需要分别处理 SSH 队列、审批、接管和并发规则。

## 四、人机共驾模式

| 模式 | Codex 权限 | 用户终端 |
|---|---|---|
| 每次询问 | 每项操作先展示并等待批准 | 完全可用 |
| 自动只读 | 安全只读命令自动执行，写操作询问 | 完全可用 |
| 信任会话 | 普通操作自动执行，高危仍需批准 | 完全可用 |

“用户接管 / Codex 暂停”是独立的会话控制状态，不是第四档授权等级。这样不会把“谁正在驾驶”和“Codex 可以自动做什么”混成同一个概念。

共同规则：

- 信任会话必须设置有效期，到期自动降级；
- 高危操作不能被普通信任会话自动放行；
- 用户开始输入时，可以暂停 Codex 并接管终端；
- 用户手动命令不受 Codex 授权等级限制，但仍受高危命令护栏、主机信任和数据边界约束；
- 主机指纹验证、凭据保护和历史脱敏对所有入口强制生效。

## 五、共驾执行流程

### 5.1 Codex 执行普通命令

1. Codex 通过 MCP 提交结构化操作；
2. 会话协调模块记录操作者为 `Codex`；
3. 授权与风险模块返回允许、需要审批或拒绝；
4. 获得授权后，操作进入当前服务器的执行队列；
5. 命令和输出实时显示在共享终端；
6. 执行结果写入共驾轨迹；
7. 退出码作为内部执行结果保存，不在终端额外制造提示噪声。

### 5.2 Codex 执行高危命令

审批卡必须展示：

- 完整命令；
- 目标服务器；
- 当前目录；
- 风险原因；
- 预计影响；
- 恢复或备份方案。

审批必须绑定命令内容、服务器、目录和有效期。Codex 修改任何一项后，原审批立即失效。

### 5.3 用户接管

1. 用户点击“接管”或直接在终端输入；
2. 未开始的 Codex 操作暂停；
3. 正在执行的操作不能被静默抢占，界面显示“等待完成”，或由用户明确发送中断；
4. 用户操作完成后，可以选择恢复 Codex；
5. 接管过程写入共驾轨迹。

## 六、界面信息架构

### 6.1 左侧：服务器星图

只负责：

- 服务器配置；
- 分组和搜索；
- 连接状态；
- 当前活跃会话。

不再重复展示授权模式和文件边界。

### 6.2 中央：共享终端

负责：

- 用户手动输入；
- Codex 命令和实时输出；
- 当前目录和真实 Shell 提示符；
- Codex 执行中、暂停和用户接管状态。

终端内容保持标准 SSH 体验。操作者身份通过终端顶部状态或命令旁的轻量标记展示，不污染远程 Shell 输出。

### 6.3 右侧：共驾轨迹

负责：

- 当前由用户还是 Codex 驾驶；
- Codex 正在分析、等待审批或执行；
- 高危审批；
- 历史操作和结果；
- 暂停、恢复和接管。

普通安全状态不长期占据卡片，只有异常或需要用户行动时才突出显示。

### 6.4 文件舱

负责：

- 展示真实服务器目录；
- 返回上一级；
- 刷新；
- 拖入上传；
- 点击选择本地文件；
- 下载和传输进度；
- 单独显示本地与远程允许范围。

授权模式只在共驾控制区展示，文件范围只在文件舱展示，连接状态只在服务器列表和会话头展示，从根源上消除重复。

## 七、并发与终端规则

- 同一共享终端同一时刻只允许一个前台命令；
- Codex 普通命令进入串行队列，避免输出交叉；
- 用户输入拥有最高优先级，可以暂停未执行的 AI 操作；
- 写操作不自动重试；
- 网络恢复后只允许重试确认无副作用的只读操作；
- 文件传输使用独立 SFTP 通道，但必须出现在同一共驾轨迹中；
- AI 命令通过内部标记识别完成状态，内部标记不得显示给用户。

### 7.1 透明终端与命令护栏

普通 SSH PTY 会把键盘字节直接发送给远程 Shell。OrbitSSH 无法在不改变终端语义的前提下，可靠预判 `vim`、`top`、Shell 补全或自定义行编辑器中的每次回车。

因此首版明确区分：

- 主机指纹、凭据保护、文件范围和历史脱敏属于强制护栏，对用户与 Codex 始终生效；
- Codex 的结构化命令始终在发送前完成风险评估和审批；
- 用户在“受保护命令模式”提交的 Shell 命令在发送回车前评估，高危命令等待确认；
- 用户进入原始交互 TTY 时，界面明确显示“原始终端”，暂停 Codex 自动操作，不宣称可以完整预判交互程序内部行为。

不能为了满足文案而假装原始 PTY 已被完整保护。

## 八、Runtime 生命周期

Runtime Host 独立于 Electron 窗口运行，由桌面端或 MCP 按需启动。

关闭桌面端时提供：

1. 仅关闭界面，保留 Codex/MCP 能力；
2. 当前任务完成后关闭 Runtime；
3. 中断任务并立即关闭全部能力。

MCP 连接到 Runtime Host，而不是直接操作 SSH。这样所有操作都无法绕过共驾轨迹和安全策略。

Windows 本地通信使用仅当前用户可访问的 Named Pipe，并校验调用方身份。

### 8.1 客户端租约与后台保活

Runtime Host 是 SSH、PTY、执行队列和待审批动作的唯一所有者。Electron 窗口与 MCP 只持有客户端租约，关闭任一客户端都不能直接销毁共享会话。

Runtime 至少维护四类租约：

- `desktop`：桌面界面已连接；
- `mcp`：一个本地 AI 客户端已连接；
- `active_action`：操作正在运行；
- `retained_session`：用户明确要求关闭界面后保留的会话。

用户选择“仅关闭界面，Codex 继续”时，只释放 `desktop` 租约，保留 `retained_session` 和正在运行的动作。重新打开 OrbitSSH 后，桌面端通过逻辑会话 ID 和事件游标重新附着，不创建新的 SSH 会话，也不重置当前目录。

如果用户选择“当前任务完成后关闭”，Runtime 在最后一个动作结束后关闭会话并退出。若动作停在等待审批状态，则审批到期后自动拒绝，再完成退出。

如果用户选择“中断并立即关闭”，Runtime 立即拒绝所有待审批动作、中断允许中断的任务、关闭 SSH 会话并退出。

### 8.2 无界面时的高危审批

桌面界面关闭后，高危操作绝不自动放行：

- 动作保持为 `pending_approval`，命令尚未发送到服务器；
- 同一会话后续 Codex 队列暂停，其他会话不受影响；
- MCP 返回等待用户审批，Windows 通知只显示脱敏摘要；
- 用户重新打开 OrbitSSH 后恢复审批卡；
- 审批绑定会话、服务器、命令摘要、工作目录和有效期；
- 到期未处理则自动拒绝，Codex 不能通过 MCP 自行批准。

### 8.3 “一直存在”的物理边界

只要 Windows 用户会话、网络和 Runtime Host 仍存活，共享 SSH/PTY 可以在 Electron 窗口关闭后继续存在。电脑重启或 Runtime 崩溃后，普通 SSH PTY 无法原样恢复交互进程；如果产品需要跨重启保留当前目录和前台程序，必须增加可选的远程 `tmux`/`screen` 会话适配器。逻辑会话和事件账本可以恢复，但不能把重新连接伪装成原 PTY 从未中断。

## 九、数据模型

至少包含：

- `connection_profiles`：服务器配置；
- `logical_sessions`：逻辑会话；
- `session_participants`：用户、Codex、系统；
- `actions`：命令或文件操作；
- `approvals`：审批内容、签名和有效期；
- `session_events`：共驾轨迹；
- `file_transfers`：上传下载记录；
- `runtime_leases`：桌面端和 MCP 的运行占用；
- `credential_refs`：Windows 凭据引用。

密码、私钥口令和 Token 不进入 SQLite。

## 十、安全规则

- Named Pipe 只允许当前 Windows 用户连接；
- MCP 不能绕过 Runtime Host 直接调用 SSH；
- 主机指纹变化时立即中止连接，且只能由用户在图形界面重新授权；
- 审批绑定操作内容的哈希、服务器、目录、风险等级和有效期；
- 命令、输出和错误在写入事件账本前统一脱敏；
- 密码和私钥口令只存入 Windows 凭据管理器；
- 高危操作没有可验证恢复方案时，可以被策略直接禁止；
- 本地和远程文件路径必须在解析真实路径后再次检查允许范围。

## 十一、首版实施顺序

1. 把 SSH 会话和执行队列迁入独立 Runtime Host；
2. 建立桌面端与 MCP 的统一操作接口；
3. 实现所有操作来源标记和共驾事件账本；
4. 实现每次询问、自动只读和信任会话；
5. 实现暂停、接管和恢复；
6. 让 Codex 命令实时显示在共享终端；
7. 重构右侧为共驾轨迹，并完成状态区去重；
8. 接入文件舱和 Runtime 关闭策略。

## 十二、验收标准

“人机共驾”完成必须同时满足：

- Codex 的命令和输出可以在桌面终端实时看到；
- 用户能够识别每项操作的发起者；
- 用户可以暂停、拒绝、打断和接管；
- Codex 无法绕过授权和高危审批；
- 用户切换服务器后返回，会话内容和目录不会丢失；
- 桌面端关闭后，可以按用户选择保留或关闭 MCP；
- 桌面端关闭且选择 Codex 继续时，Runtime 与共享会话保持运行，重新打开后能够原位附着；
- 无界面时遇到高危操作会等待并最终过期拒绝，Codex 不能自批；
- 连接、授权、文件范围和风险信息不在多个区域重复出现；
- 所有操作统一进入本地、脱敏、可恢复的共驾轨迹。

## 十三、结论

OrbitSSH 应从“桌面 SSH 工具加外挂 MCP”升级为“一个执行核心、两种驾驶入口”的协作系统。

用户始终拥有最终控制权；Codex 获得的是可见、可撤销、有时限且不能绕过安全策略的操作能力。统一 Runtime Host、会话协调模块和共驾事件账本，是实现真实人机共驾的三个核心基础。
