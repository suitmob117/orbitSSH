# OrbitSSH 实际使用问题记录

本文只记录在真实服务器操作中已经复现的问题，不把正常审批、安全护栏或尚未验证的猜测记为缺陷。

## 2026-08-04：部署 kkf-home 到 TencentCloud-2C8G

测试环境：

- OrbitSSH：Windows 安装版 `0.1.0`，代码提交 `7784fe6`
- 连接配置：`TencentCloud-2C8G`
- 会话模式：自动只读
- 操作目标：盘点现有 Docker 部署，随后备份并更新前端与后端 JAR

### ORBIT-REAL-001：引号内的管道字符被误判为复合 Shell 写操作

复现命令：

```bash
docker ps --format '{{.Names}}|{{.Image}}|{{.Status}}'
```

实际结果：命令被标记为 `write` 并进入 `pending_approval`，理由为“复合 Shell 语法不能自动确认为只读操作”。这里的 `|` 位于单引号包裹的 Docker 格式字符串中，只用于输出分隔，不是 Shell 管道。

影响：常见的 Docker 只读盘点无法在自动只读模式运行，并触发后续 Codex 队列暂停。

期望：解析器区分引号内的普通字符和 Shell 运算符；`docker ps`、`docker inspect` 等明确的查询子命令可纳入只读规则。

临时处理：避免在格式字符串中使用 `|`，或由用户明确审批。

### ORBIT-REAL-002：`sha256sum` 未被识别为只读命令

复现命令：

```bash
sha256sum /opt/portal-data-server/kkf-app/kkf-admin.jar
```

实际结果：命令被标记为 `write` 并进入 `pending_approval`，理由为“无法确认命令只读”。

影响：部署前后最常用的文件完整性校验需要人工审批，也会暂停后续 Codex 操作。

期望：在参数不包含命令执行、重定向或其他复合语法时，将 `sha256sum`、`sha512sum` 作为明确只读命令。

临时处理：使用 `stat` 检查大小和时间，并由用户审批哈希命令。

### ORBIT-REAL-003：一个误判的待审批动作会暂停后续独立只读检查

实际结果：ORBIT-REAL-001 进入待审批后，紧随其后的两个 `docker inspect` 被记录为 `paused`，理由为“当前会话存在待审批动作，后续 Codex 队列已暂停”。

影响：误判不仅阻止当前命令，还会扩大为整个 Codex 检查队列停顿；用户必须先处理审批卡，才能继续与该服务器协作。

期望：待审批动作不占用共享终端队首；至少允许与其无依赖的明确只读检查继续执行。高危动作是否冻结后续队列应与普通写操作区分。

临时处理：在真实部署前临时切换为“信任会话”，结束后切回“自动只读”；误判的审批卡需要用户及时批准或拒绝。

### ORBIT-REAL-004：MCP 命令结果包含原始终端控制序列

实际结果：`pwd`、`ls`、`stat` 等 MCP 返回的 `stdout` 中包含 `ESC[?2004l`、颜色控制码和回车字符。

影响：Codex 需要额外清洗内容，JSON 输出难读，后续若对路径、哈希或容器状态做精确解析容易受干扰。

期望：交互终端仍保留原始控制序列；MCP 的结构化命令结果和历史摘要提供去除 ANSI/终端模式控制码后的纯文本字段。

临时处理：调用方在解析前去除 ANSI 转义序列并统一换行。

### ORBIT-REAL-005：批准审批卡与切换会话授权的区别不够清楚

实际过程：提示用户把会话临时切换为“信任会话”并处理现有审批卡后，用户反馈“已经都批准了”，但 `get_session_health` 仍显示 `authorizationLevel: auto_readonly`。用户自然地把“批准当前动作”理解成已经授予部署所需权限。

影响：用户认为授权已经完成，但 Codex 继续看到自动只读；后续上传、备份、替换和重启仍会逐条进入审批并冻结队列，双方容易反复确认。

期望：审批卡明确提示“仅批准本次动作，不改变会话模式”；需要连续写操作时提供醒目的“本次会话切换为信任会话”入口，并在切换后显示即时、不可混淆的状态反馈。

临时处理：明确要求用户操作会话顶部的三档共驾模式，并通过 `get_session_health.authorizationLevel` 复核，而不是仅询问是否已经批准。

### ORBIT-REAL-006：异步批准后的文件传输结果无法回传给 MCP 调用方

复现过程：

1. MCP 请求把本地 JAR 上传到 `/opt/portal-data-server/kkf-app/kkf-admin.jar.new`。
2. `upload_file` 只返回 `pending_approval` 和动作 ID。
3. 用户在桌面端批准上传。
4. 随后通过 `stat` 检查，远端临时文件不存在。
5. 后续从本地 SQLite 确认连接配置已经保存 `localTransferRoot: D:\\Code\\kkf-home` 和远程允许目录 `/opt`，但活动会话仍使用建立连接时的旧配置；桌面端批准后才短暂显示“未配置本地文件传输允许目录”。MCP 无法取得该最终错误对象。

影响：Codex 不知道异步动作最终是成功还是失败，也拿不到失败原因；若没有额外的远端校验，可能把“用户已批准”误当作“传输已完成”。

期望：MCP 提供按动作 ID 查询最终状态与结果的工具，或让原始工具调用在审批完成后继续返回；失败结果应明确指出缺少本地允许目录等可修复原因。

临时处理：每个异步文件操作后使用独立只读命令验证远端路径、大小和哈希；部署前先检查连接配置同时具备本地与远程允许目录。

### ORBIT-REAL-007：待审批卡片在协作轨迹中的位置与时间顺序不一致

实际结果：真实部署产生待审批上传动作后，`10:23:32` 的待审批卡被插在两组历史记录之间；卡片下方又出现 `10:14:45`、`10:14:48` 和 `10:22:01` 的历史项。同一命令还分别以共驾动作和执行记录出现，视觉上像重复记录。

影响：用户难以判断哪一项是当前必须处理的操作，也无法从纵向轨迹理解真实先后关系；记录变多后，待审批卡可能离当前视线较远。

期望：

- 待审批、进行中和排队中动作放入独立的“当前操作”区域，并保持醒目可见；
- 已完成、失败和拒绝的项目进入统一历史时间轴；
- 共驾动作与对应执行结果按动作 ID 或关联 ID 合并展示，避免重复；
- 所有历史来源合并后再按同一时间字段排序，不分别排序后拼接。

临时处理：从状态标签和时间判断当前卡片；界面修复前不在部署过程中重启客户端，以免打断共享会话。

### ORBIT-REAL-008：修改文件传输范围后，已连接会话继续使用旧配置

复现过程：

1. 先建立 `TencentCloud-2C8G` SSH 会话，再在服务器配置中补充本地允许目录 `D:\Code\kkf-home` 和远程允许目录 `/opt`。
2. `list_connection_profiles` 与 SQLite 均确认新配置已保存。
3. 在原活动会话中提交 JAR 上传并批准，动作立即从 `running` 变为 `failed`，桌面端提示“未配置本地文件传输允许目录”。
4. 只断开并重新建立该连接后，新会话才读取到文件传输范围。

影响：配置页显示保存成功，但当前会话仍按旧边界拒绝传输；用户无法判断需要重连，且失败原因只在顶部短暂出现。真实部署因此连续失败多次。

期望：保存影响文件边界的配置后，应安全刷新活动会话中的非认证配置；如果不能热更新，则明确提示“需重新连接后生效”，并提供一键重连。动作历史应保留具体失败原因。

临时处理：修改 `localTransferRoot` 或 `remoteTransferRoots` 后，先断开并重新连接，再提交文件传输。

### ORBIT-REAL-009：实际高危的发布切换事务只被标记为普通写操作

复现命令：

```bash
mv /opt/portal-data-server/web/html /opt/portal-data-server/web/html.previous-20260804-1108 && mv /opt/portal-data-server/releases/20260804-1108/web-html /opt/portal-data-server/web/html && docker restart portal-data-server-nginx-1
```

实际结果：该命令会替换生产前端目录并重启 Nginx，影响线上服务可用性与发布结果，但 OrbitSSH 只标记为 `risk: write`，理由为“复合 Shell 语法不能自动确认为只读操作”，没有识别其中的 `mv` 生产目录切换和 `docker restart`。

影响：普通写操作与真正的生产发布、高危切换在审批卡上没有明显差异，用户容易低估影响范围；也不符合界面“仅高危操作醒目标记”的设计目标。

期望：复合命令应逐个分析子命令并采用最高风险等级；涉及覆盖或移动生产路径、容器重启、服务停止的动作至少标记为 `high`，审批卡应展示受影响路径、容器和回滚点。

临时处理：Codex 在提交复合发布事务前主动说明每个子步骤、影响范围和回滚目录，不能依赖当前风险标签。

### ORBIT-REAL-010：操作结果提示一直不自动消失

状态：已修复。消息使用显式的成功、错误和阻塞类型管理；成功提示 4 秒后自动收起，普通错误提示保留 8 秒并可手动关闭，需要继续处理的主机指纹提示保持显示。相同提示再次出现会重新计时，旧计时器不会误删新提示。

实际结果：执行审批等操作后，工作台顶部持续显示“操作已批准并执行”，后续没有新消息时也不会自动收起，占用界面空间并让用户误以为当前仍有操作正在处理。

影响：瞬时反馈与持续状态混在一起；用户无法判断消息是刚发生、仍在进行，还是已经完成很久的历史提示。

期望：成功类提示在 3～5 秒后自动淡出；普通错误可保留更长时间并提供关闭按钮；需要用户处理的阻塞错误才持续显示。新消息到来时应重置计时器，组件卸载或消息替换时必须清理旧计时器。

### ORBIT-REAL-011：Windows 安装版中的 OrbitSSH 品牌图标丢失

状态：已修复。品牌图标改为由构建工具追踪的资源 URL，并提供字母回退；生产构建和隔离 Electron 渲染冒烟均确认图片已加载。

实际结果：应用安装完成后，左上角 OrbitSSH 品牌位置显示损坏图片占位符，而开发环境中的相关界面并非预期如此。

影响：安装成品的品牌识别受损，也说明渲染进程使用的图片路径或打包资源清单在生产环境下不可靠；同类静态资源可能存在相同风险。

期望：品牌图标通过构建工具可追踪的资源导入或稳定的打包资源 URL 加载，并确认图标文件被纳入安装包；图片加载失败时提供不会显示破图标记的内置回退。安装包构建后增加一次资源存在性与渲染冒烟检查。

### ORBIT-REAL-012：Codex 协作通道状态灯外观像开关

状态：已修复。原开关轨道和滑块已替换为圆形呼吸状态灯及“已开启”文字，组件仅表达状态，不提供点击反馈。

实际结果：左下角“Codex 协作通道”右侧使用带轨道、发光滑块的绿色控件，视觉语言与应用内已开启的开关一致，但这里实际表达的是通道状态，并不是供用户切换的开关。

影响：用户会自然地认为点击这里可以关闭或开启协作通道，产生错误操作预期；状态展示与控制入口的职责不清。

期望：改成明确的只读状态指示器，例如圆形呼吸灯配“已连接/已开启”文字，去掉开关轨道、滑块结构、悬停手型和可点击反馈。如果未来确实提供开关，应单独设计带明确标签和状态变化说明的控制项。
